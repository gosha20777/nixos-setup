# hosts/

One directory per machine. Each holds everything that is specific to *that*
physical computer; the shared module trees under `modules/` (auto-imported by
`hosts/common.nix`) are host-agnostic and applied to every host here.

```
hosts/
  common.nix                 # shared wiring: import-trees modules/nixos/core,
                             #   home-manager sharedModules = modules/home, systemSettings
  dev/
    default.nix              # hostname, bootloader/system overrides, role imports,
                             #   per-host home attach
    home.nix                 # per-host user overrides (bar position, outputs, ...)
    hardware-configuration.nix  # generated by nixos-generate-config (committed)
```

`flake.nix` **auto-discovers** these: every directory under `hosts/` becomes
`nixosConfigurations.<dirname>`. Adding a machine means adding a directory —
you never edit `flake.nix`. (`common.nix` is a file and doesn't match the
directory filter.)

## Why hardware-configuration.nix is committed

Nix flakes only evaluate files that Git tracks, so a per-host
`hardware-configuration.nix` has to be committed for `nixos-rebuild --flake`
to see it. The file contains LUKS/disk **UUIDs** and the filesystem layout — those
are device *identifiers*, not secrets (a UUID gives no one access to an
encrypted volume; the passphrase does). Committing them makes the repo a true
source of truth: the running machine is fully described by these files.

## What goes in `hosts/<name>/` vs the shared modules

| Belongs in `hosts/<name>/` | Belongs in `modules/` |
|---|---|
| `hardware-configuration.nix` (disk UUIDs, filesystems, swapDevices) | Everything auto-imported: `modules/nixos/core/*`, `modules/home/*` |
| `networking.hostName` | Bootloader defaults, services, system packages, the user, PipeWire, niri/Noctalia |
| The `nixos-hardware` module for the exact model | Hardware-class roles (`modules/nixos/roles/{laptop,desktop}.nix`) — opt-in from the host |
| Bootloader/system overrides (dev VM forces GRUB/BIOS) | |
| Hibernation swap LUKS unlock + `boot.resumeDevice` | |
| `home.nix` — user-level overrides (bar position, outputs) | |
| `systemSettings.*` overrides (terminal, git identity) | |

## Standing up a new machine

1. **Install a base NixOS** and boot it (see `../INSTALL.md` for the dev VM
   path; real hardware follows the same shape with a different
   `nixos-hardware` module).
2. **Clone this repo** into `~/Projects/my_projects/nixos-setup` (the repo
   directory is the live config — there is no `/etc/nixos` symlink; builds
   point at the flake path directly).
3. **Scaffold the host directory** (copies this machine's generated hardware
   config in, writes a `default.nix` + `home.nix`, auto-detects the swap LUKS
   UUID when it can, and git-adds all three):
   ```bash
   cd ~/Projects/my_projects/nixos-setup
   scripts/new-host.sh            # uses the current hostname
   # or: scripts/new-host.sh my-other-laptop
   ```
4. **Review `hosts/<hostname>/default.nix`:**
   - Set the right [`nixos-hardware`](https://github.com/NixOS/nixos-hardware)
     module for the model (the template defaults to the Framework 13 AMD
     Ryzen 7040).
   - Pick a role: uncomment `../../modules/nixos/roles/laptop.nix` or
     `desktop.nix` in the imports.
   - Confirm or complete the hibernation swap block. If `new-host.sh` found
     active swap on a `luks-<uuid>` mapper it's filled in; otherwise find the
     swap partition's LUKS UUID and fill it in:
     ```bash
     swapon --show
     lsblk -o NAME,TYPE,FSTYPE,UUID
     ```
     (Drop the block entirely if you don't want hibernation — suspend-to-RAM
     still works.)
5. **Build it:**
   ```bash
   sudo nixos-rebuild switch --flake .#<hostname>
   ```
6. **Commit** the new host directory (and `flake.lock` if the build generated
   one):
   ```bash
   git add hosts/<hostname> flake.lock
   git commit -m "hosts: add <hostname>"
   git push
   ```

## Determinism note

Because every host shares the same auto-imported module trees and pins the
same `flake.lock`, two machines built from the same commit get the *same*
package set, services, and dotfiles. They differ only by the contents of
their `hosts/<name>/` directory (and any `systemSettings` overrides) — which
is exactly the hardware and deployment choices that genuinely differ
between them.
