# Декларативная разметка накопителей: Disko, Btrfs, Timeshift и zramSwap

В данном документе описана организация дисковой подсистемы репозитория: отказ от устаревшего файла `hardware-configuration.nix`, устройство Btrfs-субтомов, оптимизации под NVMe SSD и стратегия подкачки в оперативной памяти.

---

## 1. Архитектура: Шаблоны и переопределения («Shared Templates + Local Overrides»)

Исторически NixOS требовала запуска `nixos-generate-config` на уже установленной машине с последующим коммитом сгенерированного файла `hardware-configuration.nix`, хранящего захардкоженные UUID разделов. Это затрудняло автоматизацию и развертывание на чистые накопители.

В этом проекте разметка полностью переведена на **`disko`**:
* Диски и точки монтирования описываются декларативно как код.
* Шаблоны лежат в каталоге `modules/disko/`.
* Хост импортирует нужный шаблон и при необходимости переопределяет только физическое имя устройства (например, `/dev/nvme0n1` или `/dev/vda`).

## 2. Разбор шаблона `modules/disko/btrfs-uefi.nix` (Для современных ПК и ThinkPad)

Шаблон предназначен для всех современных компьютеров с поддержкой чистого UEFI:

```nix
{ lib, ... }:
{
  disko.devices = {
    disk.main = {
      type = "disk";
      device = lib.mkDefault "/dev/nvme0n1";
      content = {
        type = "gpt";
        partitions = {
          # Загрузочный раздел ESP
          ESP = {
            size = "1G";
            type = "EF00";
            content = {
              type = "filesystem";
              format = "vfat";
              mountpoint = "/boot";
              mountOptions = [ "umask=0077" ];
            };
          };

          # Основной Btrfs раздел
          root = {
            size = "100%";
            content = {
              type = "btrfs";
              extraArgs = [ "-f" ];
              subvolumes = {
                "@"          = { mountpoint = "/";          mountOptions = [ "compress=zstd:3" "noatime" "discard=async" "space_cache=v2" ]; };
                "@home"      = { mountpoint = "/home";      mountOptions = [ "compress=zstd:3" "noatime" "discard=async" "space_cache=v2" ]; };
                "@nix"       = { mountpoint = "/nix";       mountOptions = [ "compress=zstd:3" "noatime" "discard=async" "space_cache=v2" ]; };
                "@log"       = { mountpoint = "/var/log";   mountOptions = [ "compress=zstd:3" "noatime" "discard=async" "space_cache=v2" ]; };
                "@snapshots" = { mountpoint = "/.snapshots"; mountOptions = [ "compress=zstd:3" "noatime" "discard=async" "space_cache=v2" ]; };
              };
            };
          };
        };
      };
    };
  };
}
```

### Почему раздел EFI монтируется в `/boot`, а не в `/boot/efi`?
В традиционных дистрибутивах (Fedora, Ubuntu) с загрузчиком GRUB используется раздельная схема: `/boot` (ext4 с ядрами) и вложенный `/boot/efi` (FAT32 с бинарником grub).  
В **NixOS с загрузчиком `systemd-boot`**:
1. Раздел ESP (FAT32, тип `EF00`, размер 1 ГБ) монтируется **напрямую в `/boot`**.
2. Прошивка UEFI материнской платы напрямую считывает `systemd-boot`, а загрузчик считывает ядра и initrd с того же раздела FAT32.
3. Это исключает лишнюю вложенность, ускоряет запуск и является нативным стандартом спецификации UEFI.

## 3. Архитектура субтомов и совместимость с Timeshift

Btrfs позволяет создавать логические субтомы (subvolumes) с независимыми деревьями снимков:

| Субтом | Точка монтирования | Назначение | Особенности |
| :--- | :--- | :--- | :--- |
| **`@`** | `/` | Корень операционной системы | Жесткое требование Timeshift в режиме BTRFS. Снимки корня делаются мгновенно. |
| **`@home`** | `/home` | Пользовательские данные и проекты | Жесткое требование Timeshift. Защищает документы и код от случайного удаления. |
| **`@nix`** | `/nix` | Хранилище пакетов Nix Store | **КРИТИЧНО:** Изолирован от корня `@`. Если бы `/nix` лежал внутри `@`, снимки замораживали бы десятки гигабайт пакетов, и сборщик мусора `nix-collect-garbage` не мог бы физически освободить место на SSD. |
| **`@log`** | `/var/log` | Системные журналы systemd | Сохраняет историю ошибок и системных логов даже при откате корневого субтома `@` на предыдущее состояние. |
| **`@snapshots`**| `/.snapshots` | Каталог хранения локальных снимков | Точка привязки для утилит резервного копирования. |

## 4. Оптимизация под NVMe SSD (Samsung PM981 / 3D TLC)

На современных накопителях NVMe (как `Samsung MZVLB512HBJQ` на контроллере Phoenix) критически важно минимизировать коэффициент усиления записи (Write Amplification) и обеспечить плавный I/O:

1. **`noatime`:** Отключает постоянное обновление метки времени последнего доступа к файлам при чтении. Устраняет гигабайты паразитных фоновых записей на флеш-память.
2. **`compress=zstd:3`:** Прозрачное сжатие данных на лету алгоритмом Zstandard 3-го уровня:
   * Физический объем записей на TLC-ячейки снижается на **30–50%**.
   * Скорость чтения вырастает: процессор i7 распаковывает zstd со скоростью нескольких гигабайт в секунду, что быстрее считывания несжатых байт с флеш-чипов.
3. **`discard=async`:** Асинхронный TRIM (появился в ядре Linux 5.6). Контроллер SSD получает команды очистки освободившихся блоков пачками в фоне, без микрофризов и блокировки шины ввода-вывода (в отличие от синхронного `discard`).
4. **`space_cache=v2`:** Быстрый алгоритм отслеживания свободных блоков на диске.
5. **Еженедельный таймер fstrim:**
   ```nix
   services.fstrim.enable = true;
   ```

## 5. Стратегия подкачки: `zramSwap` в оперативной памяти

На хосте ThinkPad установлено **32 ГБ оперативной памяти DDR4**.

### Почему мы полностью отказались от файла подкачки на SSD:
* **Скорость:** Скорость RAM DDR4 составляет **~25–30 ГБ/с** против **~2–3 ГБ/с** у быстрого NVMe SSD.
* **Ресурс накопителя:** **0 байт записей на SSD**. Своп не изнашивает ячейки памяти.
* **Динамическое выделение:** zram создается в памяти, но в простое занимает **0 байт**. Память расходуется только тогда, когда ядро вытесняет неактивные страницы.

### Конфигурация:
```nix
zramSwap = {
  enable = true;
  algorithm = "zstd";
  memoryPercent = 25; # 8 ГБ виртуального свопа
};
```

### Математика расхода памяти при `memoryPercent = 25`:
* Максимальный виртуальный размер: **8 ГБ**.
* При среднем коэффициенте сжатия `zstd` ~2.7:1, даже при 100% заполнении свопа в реальной памяти это займет всего:
  $$8\text{ ГБ} / 2.7 \approx 2.9\text{ ГБ физической RAM}$$
* Минимум **28–29 ГБ быстрой RAM** всегда гарантированно остаются доступными под браузер, компиляторы и дисковый кэш.

## 6. Масштабирование на многодисковые хосты (2+ диска, RAID)

Если в парке появится сложный компьютер с несколькими накопителями (например, ПК с NVMe под систему и SATA SSD под `/home` или RAID-массивом):

1. **Изоляция:** Хост **НЕ импортирует** шаблоны `modules/disko/btrfs-*.nix`.
2. **Локальный профиль:** В директории хоста создается собственный файл `hosts/<hostname>/disko.nix`:
   ```nix
   {
     disko.devices = {
       disk.system = { device = "/dev/nvme0n1"; ... };
       disk.storage = { device = "/dev/sda"; ... };
     };
   }
   ```
3. Никакие общие файлы репозитория при этом не модифицируются.
